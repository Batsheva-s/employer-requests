# ביצועים על 100,000 פניות

המסמך מראה איך הפתרון עובד מול 100,000 פניות: איך נמנעת טעינה של כל הנתונים, מה כל אינדקס נותן, מה SQL Server עושה בפועל בכל שאילתה, מה שונה בעקבות המדידה, ומה צוואר הבקבוק ואיך אפשר לשפר אותו.

כל מספר כאן נמדד – שום דבר לא הוערך:

* **ה-SQL** הוא בדיוק מה ש-EF Core שולח, כפי שנרשם בלוג של האפליקציה, ורץ מתוך [`performance/measure.sql`](performance/measure.sql) עם `SET STATISTICS IO, TIME ON`.
* **תוכניות הביצוע** הן תוכניות בפועל (Actual Execution Plans) של אותה הרצה, שמורות ב-[`performance/plans`](performance/plans) – כל קובץ נפתח ב-SSMS כתרשים.
* **זמני ה-API** נמדדו מבחוץ, כולל HTTP, בעזרת [`performance/time_api.py`](performance/time_api.py).

| סביבת המדידה | |
|---|---|
| איך | ה-Workflow [`performance.yml`](../.github/workflows/performance.yml), שרץ ידנית ב-GitHub Actions ומצרף להרצה את כל הפלט |
| מכונה | GitHub Actions: ‏4 ליבות (AMD EPYC 7763), ‏16GB |
| בסיס נתונים | SQL Server 2022 Developer (16.0.4305.5) ב-Docker, ‏Collation ‏`SQL_Latin1_General_CP1_CI_AS` – כמו ב-LocalDB |
| נתונים | ‏100,000 פניות מפקודת `seed`. הטבלה: ‏1,948 דפים של 8KB ‏(15.2MB) |
| מצב | הנתונים בזיכרון (הרצה שנייה של הסקריפט), כמו בשרת שנמצא בשימוש |

**במספרים:** "קריאות" הן Logical Reads – מספר הדפים (8KB) ש-SQL Server קרא. זה המדד היציב: הוא לא תלוי במכונה או בעומס. הזמנים הם זמן CPU של השאילתה.

## תקציר

* **רוב הקריאות ל-API לוקחות פחות מ-15ms, וכולן – חוץ מהחיפוש החופשי – פחות מ-75ms,** כי כל סינון ומיון נפוץ נשען על אינדקס, ועמוד ראשון נקרא בעשרות דפים בלבד.
* **צוואר הבקבוק הוא החיפוש החופשי** (`LIKE '%טקסט%'`): הוא לא יכול להשתמש באינדקס, ולכן סורק את כל הטבלה – כ-300ms לרשימה וכ-470ms לסיכום. העלות היא CPU, לא קריאה מהדיסק. ההצעות לשיפור, עם מדידות: [סעיף 6](#6-צוואר-הבקבוק-החיפוש-החופשי).
* **המדידה מצאה בעיה, והיא תוקנה:** הסינון לפי מטפל קרא את כל האינדקס במקום לחפש בו (444 דפים במקום 16). [סעיף 5](#5-מה-שונה-בעקבות-המדידה).
* **אינדקס שנבדק ולא עזר – לא נוסף.**

## 1. איך נמנעת טעינה של כל הנתונים לזיכרון

כל פעולה היא שאילתה אחת ש-SQL Server מריץ במלואה, ורק התוצאה הסופית יוצאת מבסיס הנתונים. כך נראה העמוד הראשון של הרשימה, בלי סינון:

```sql
SELECT COUNT(*)
FROM [Requests] AS [r];

SELECT [r].[Id], [r].[Title], [r].[OrganizationName], [r].[Status], [r].[Priority], [r].[AssignedTo], [r].[CreatedAt], [r].[UpdatedAt], [r].[RowVersion]
FROM [Requests] AS [r]
ORDER BY [r].[CreatedAt] DESC, [r].[Id] DESC
OFFSET @__p_0 ROWS FETCH NEXT @__p_1 ROWS ONLY;
```

והנתונים המסכמים – קיבוץ בבסיס הנתונים, ולכן יוצאות ממנו 12 שורות (4 סטטוסים × 3 עדיפויות) ועוד 5, ולא 100,000:

```sql
SELECT [r].[Status], [r].[Priority], COUNT(*)
FROM [Requests] AS [r]
GROUP BY [r].[Status], [r].[Priority];

SELECT TOP(@__p_0) [r].[AssignedTo], COUNT(*)
FROM [Requests] AS [r]
WHERE [r].[AssignedTo] IS NOT NULL AND [r].[Status] <> CAST(4 AS tinyint)
GROUP BY [r].[AssignedTo]
ORDER BY COUNT(*) DESC, [r].[AssignedTo];
```

| מה | איפה זה קורה | בקוד |
|---|---|---|
| סינון | `WHERE` | `ApplyFilter` ב-[`RequestQueryExtensions`](../src/EmployerRequests.Infrastructure/Data/RequestQueryExtensions.cs) |
| מיון | `ORDER BY`, ‏`Id` שובר שוויון | `ApplySorting` |
| דפדוף | `OFFSET / FETCH` – רק 20 שורות | `Skip` / `Take` ב-[`RequestRepository`](../src/EmployerRequests.Infrastructure/Data/RequestRepository.cs) |
| עמודות | רק מה שה-DTO צריך | `Select` ל-`RequestListItemDto` בתוך השאילתה |
| סיכום | `GROUP BY` | `CountByStatusAndPriorityAsync`, ‏`GetTopAssigneesAsync` |
| ביטול | `CancellationToken` עד SQL Server | כל מתודה אסינכרונית מקבלת אותו |

בנוסף: `AsNoTracking` בכל קריאה (אין עלות של מעקב שינויים), ו-`COUNT` נפרד לחישוב מספר העמודים. אם העמוד המבוקש אחרי העמוד האחרון – השאילתה השנייה לא נשלחת בכלל.

* **המחיר של האינדקסים:** ‏1,655 דפים (12.9MB) לצד טבלה של 15.2MB. כל הוספת פנייה כותבת לחמשת המבנים. שינוי סטטוס מעדכן את שני האינדקסים שבהם `Status` הוא מפתח, ועדיין לוקח 5.4ms בממוצע מקצה לקצה (תרחיש 13). שורת ההיסטוריה וה-UPDATE, כולל קריאת הגרסה הנוכחית לפניהם – 13 קריאות (13.1).
* **מה לא קיבל אינדקס:** מיון לפי כותרת או לפי זמן עדכון (נדיר; סריקה ומיון כמו 1.3 – כ-40ms), והחיפוש החופשי – אינדקס לא עוזר ל-`LIKE '%…%'` ([סעיף 6](#6-צוואר-הבקבוק-החיפוש-החופשי)).

ארבעה דברים שרואים בתוכניות:

1. **SQL Server עוצר כשיש לו 20 שורות (Row Goal).** בעמוד ראשון הוא עובר על הפניות מהחדשה לישנה, בודק כל אחת, ועוצר אחרי 20 שמתאימות (1.2, ‏3.2, ‏4.2, ‏7.2). לכן גם עמוד ראשון של חיפוש טקסט מהיר – הבעיה היא ה-`COUNT`, שחייב לעבור על הכול.
2. **`LIKE 'טקסט%'` הופך לטווח באינדקס.** כשהערך מגיע כפרמטר, SQL Server מחשב את הטווח בזמן הריצה (‏Constant Scan ו-Compute Scalar לפני ה-Index Seek) – 4.1, ‏6.1.
3. **שני אינדקסים יחד.** כשיש שני תנאים, SQL Server מחפש בכל אינדקס בנפרד ומצליב את המזהים (5.1).
4. **תוכנית אחת לכל ערכי הפרמטרים (Parameter Sniffing).** ‏SQL Server מקמפל תוכנית בפעם הראשונה ומשתמש בה שוב לכל ערך. התוכנית של עמוד 1 מצוינת לעמוד 1, אבל בעמוד 2,000 היא עושה 40,000 Key Lookups ‏(8.1). התוכנית של חיפוש מילה נפוצה מצוינת למילה נפוצה, אבל במילה שלא מופיעה היא עוברת על כל הטבלה דרך האינדקס, שורה-שורה (7.4). בקבצי התוכניות רואים את זה ב-`ParameterCompiledValue`: התוכנית של 8.1 קומפלה ל-`OFFSET 0`, וזו של 7.4 – ל-`'%אישור%'`.

## 5. מה שונה בעקבות המדידה

### הסינון לפי מטפל/ת – תוקן

**מה נמדד:** הספירה של פניות "שרה…" קראה 444 דפים – כל האינדקס – ולקחה 22ms, בזמן שהספירה המקבילה לפי ארגון קראה 33.

**למה:** הקוד היה `AssignedTo != null && AssignedTo.StartsWith(prefix)`, ו-EF Core תרגם אותו ל-`[AssignedTo] IS NOT NULL AND [AssignedTo] LIKE @prefix`. בתוכנית רואים ש-SQL Server חיפש באינדקס לפי `IS NOT NULL` – כל השורות שיש להן מטפל, כמעט כל האינדקס – ובדק את ה-`LIKE` על כל אחת מהן.

**התיקון:** בלי בדיקת ה-null. ב-SQL, ‏`NULL LIKE 'x%'` לעולם לא מתקיים, כך שהיא לא נחוצה; ה-`!` בקוד רק מודיע לקומפיילר שהביטוי לא רץ בזיכרון.

| | לפני | אחרי |
|---|---|---|
| ספירה (6.1) | 444 קריאות, 22ms | **16** קריאות, **2ms** |
| תרחיש 6 ב-API | 59ms בממוצע | **34ms** |

### אינדקס שנבדק ולא נוסף

עמוד של מטפל/ת, ממוין לפי עדיפות (6.2), סורק את כל הטבלה: ל-SQL Server זול יותר לקרוא 1,944 דפים מאשר לבצע 2,938 Key Lookups. נבדקה הוספה של `INCLUDE (Priority, CreatedAt)` לאינדקס, כדי שהמיון יקרה בתוך האינדקס ורק 20 השורות של העמוד ייקראו מהטבלה. התוצאה: התוכנית לא השתנתה (1,944 קריאות, 28ms). אינדקס שלא עוזר לא נוסף – הוא רק היה מגדיל את הכתיבה.

## 6. צוואר הבקבוק: החיפוש החופשי

**מה נמדד:** חיפוש "אישור" – 296ms ל-`COUNT` ‏(7.1), ‏301ms ו-170ms לשתי שאילתות הסיכום (11.1, ‏11.2). ב-API: ‏304ms לרשימה, ‏473ms לסיכום. חיפוש שלא מוצא כלום הוא המקרה הגרוע: ‏327ms ל-`COUNT` ו-474ms לעמוד הראשון (7.3, ‏7.4).

**למה:** ‏`LIKE '%אישור%'` מתחיל ב-`%`, ולכן אין טווח לחפש בו באינדקס: כל שורה נבדקת – כותרת ושם ארגון. הקריאה עצמה זולה (1,944 דפים מהזיכרון). **העלות היא CPU:** ה-Collation של העמודות משווה טקסט לפי כללי שפה (למשל, בלי הבדל בין אותיות גדולות לקטנות), וזו פעולה יקרה לכל תו. ההוכחה: אותה סריקה בדיוק, עם השוואה בינארית, לוקחת 29ms במקום 296ms ‏(14.1).

**מה זה אומר:** חיפוש אחד (רשימה וסיכום) צורך כ-0.77 שניות CPU. בשרת עם 4 ליבות זה בערך 5 חיפושים בשנייה לכל היותר. העלות גדלה ליניארית עם הטבלה: במיליון פניות, כל שאילתה כזו תיקח כ-3 שניות (הערכה).

**מה כבר מצמצם את הבעיה:**
* הממשק מחכה 300ms אחרי ההקשה האחרונה (Debounce) – חיפוש אחד למילה, לא חיפוש לכל אות.
* חיפוש חדש מבטל את הקודם, עד SQL Server (`switchMap` ו-`CancellationToken`) – חיפוש שהמשתמש כבר לא מחכה לו לא ממשיך לצרוך CPU.
* העמוד הראשון של מילה נפוצה מהיר (7.2), כך שהרשימה מתמלאת מהר; הספירה היא החלק היקר.

**הצעות לשיפור, מהקטנה לגדולה:**

| | הצעה | מה נמדד | מחיר |
|---|---|---|---|
| 1 | **עמודת חיפוש עם השוואה בינארית:** עמודה מחושבת ושמורה `SearchText = UPPER(Title + N' ' + OrganizationName)` עם Collation ‏`Latin1_General_100_BIN2`, והחיפוש `SearchText LIKE UPPER(@text)` | סריקה עם השוואה בינארית: 29ms; עם `UPPER` משני הצדדים, כדי שהחיפוש יישאר בלי הבדל בין אותיות גדולות לקטנות: ‏36ms ‏(14.2) – פי 8 פחות CPU | עמודה נוספת בטבלה. עדיין סריקה, שגדלה ליניארית. מבחין בין אותיות עם ובלי ניקוד |
| 2 | **Full-Text Search:** ‏`CONTAINS(..., '"אישור*"')`, עם מפרק המילים של SQL Server לעברית | – (‏LocalDB לא כולל Full-Text Search) | חיפוש באינדקס – לא סריקה. אבל המשמעות משתנה: מוצא מילים שמתחילות בטקסט, ולא כל רצף תווים ("שור" לא ימצא "אישור"). דורש החלטה מוצרית ו-SQL Server מלא |
| 3 | **שאילתת סיכום אחת:** ‏`GROUP BY Status, Priority, AssignedTo` – עד 372 שורות – והחישוב של שלושת הסיכומים מהן | – | סריקה אחת במקום שתיים לכל סיכום מסונן – בחיפוש, לפי הערכה, כ-300ms במקום כ-470ms. שינוי בקוד, לא בבסיס הנתונים |

ההמלצה: 1 ו-3 עכשיו – שינויים קטנים, שקל למדוד ולהחזיר. ‏2 כשהנפח גדל, אחרי החלטה על משמעות החיפוש.

## 7. ממצאים נוספים

**דפדוף עמוק.** עמוד 2,000 (‏`OFFSET 39,980`) קורא 122,602 דפים ולוקח 51ms ‏(8.1; ‏70ms ב-API), כי התוכנית שנבנתה לעמוד 1 עושה Key Lookup לכל שורה שמדלגים עליה. שתי חלופות נמדדו:

| | קריאות | CPU (ms) |
|---|---|---|
| ‏`OFFSET` – כמו היום (8.1) | 122,602 | 51 |
| ‏`OFFSET` על האינדקס בלבד, ואז 20 השורות (14.4) | 162 | 4 |
| ‏Keyset – "המשך אחרי השורה האחרונה שראיתי" (14.3) | 65 | 0 |

‏Keyset הוא המהיר והיציב ביותר, אבל משנה את הממשק: "הבא / הקודם" במקום קפיצה לעמוד מסוים. ‏`OFFSET` על האינדקס הוא שינוי פנימי בשאילתה, בלי שינוי בממשק. משתמשים כמעט לא מגיעים לעמוד 2,000, ולכן זה לא שונה בשלב הזה.

**סיכום מסונן לפי עדיפות.** ‏SQL Server מציע בתוכנית אינדקס על `Priority` (‏Missing Index, ב-10.1 ו-10.2). לא נוסף: סיכום מסונן לפי עדיפות אינו המסך המרכזי, והוא לוקח 42ms.

## 8. להריץ את המדידות

1. **נתונים:** ‏`dotnet run --project src/EmployerRequests.Api -- seed`.
2. **SQL:** לפתוח את [`performance/measure.sql`](performance/measure.sql) ב-SSMS, ‏Ctrl+M (Include Actual Execution Plan), ולהריץ פעמיים. בלשונית Messages – הקריאות והזמנים; בלשונית Execution plan – התוכניות.
3. **API:** להריץ את השרת, ואז `python docs/performance/time_api.py` (Python 3.10 ומעלה, בלי חבילות נוספות). הסקריפט משנה באמת את הסטטוס של פניות 1–55, ולכן אחריו כדאי ליצור את הנתונים מחדש.
4. **ה-SQL ש-EF Core שולח:** להריץ את השרת כך: `dotnet run --project src/EmployerRequests.Api -- --Logging:LogLevel:Microsoft.EntityFrameworkCore.Database.Command=Information`.
5. **התוכניות שנשמרו:** כל קובץ ב-[`performance/plans`](performance/plans) נפתח ב-SSMS כתרשים. הן נחתכו מפלט ההרצה בעזרת [`export_plans.py`](performance/export_plans.py).
6. **הכול יחד, בענן:** ‏Actions ← Performance ← Run workflow. הפלט – זמני ה-API, הסטטיסטיקות, התוכניות והלוג עם ה-SQL – מצורף להרצה.

המספרים במכונה אחרת יהיו שונים; הקריאות והתוכניות יהיו כמעט זהות.
